# Atlas 风扇「预设 / 配置」设计（v0.3 草案）

> 分支：`fan-profiles`　|　状态：设计 + 可运行原型（UI 在分支上）
> 相关实现：`src/Atlas.Core/FanPresets.cs`、`src/Atlas.Core/AtlasConfig.cs`、`src/Atlas.App/Controls/SceneBar.xaml`、`src/Atlas.App/MainWindow.xaml(.cs)`、`src/Atlas.App/CurveEditorWindow.xaml(.cs)`

## 1. 结论先行

**把「模板」「场景」「配置」彻底拆成三个词，各自只承担一件事：**

| 层次 | 用户看到的词 | 作用范围 | 能否修改 | 怎么产生 |
| --- | --- | --- | --- | --- |
| L1 内置场景 | **内置场景 · 静音 / 均衡 / 性能** | 所有未锁定风扇 | ❌ 只读 | 程序内置 |
| L2 曲线模板 | **模板 · 静音 / 均衡 / 性能** | 单个风扇的曲线 | ❌ 只读 | 程序内置（与 L1 同源） |
| L3 我的配置 | **我的配置 · 用户命名** | 所有风扇的整套热设置 | ✅ 可另存为/保存/改名/删除 | 用户「另存为…」或编辑后「保存」 |
| L4 当前方案 | **当前方案** | 实时生效的草稿 | ✅ 随时编辑 | 应用 L1/L3 或手工调整后得到 |

四层关系：

```
内置场景（一键） ──套用到所有未锁定通道──▶ 当前方案（可编辑的草稿）
曲线模板（单扇导入值）──套用到单通道──▶ 当前方案
我的配置（用户快照）──套用到所有未锁定通道──▶ 当前方案
当前方案 ──「另存为…」/「保存」──▶ 我的配置（新的或更新）
```

记忆点一句话：**预设/模板永远只读，能编辑的永远是「当前方案」，想留住修改就「保存为我的配置」。**

## 2. 现状与问题

v0.2 已有：

- 每个风扇通道三种**工作模式**：BIOS 默认 / 固定 PWM / 温度曲线。
- 单扇曲线编辑器里有三个**快捷预设**：静音 / 均衡 / 性能（点一下填充曲线点）。
- 一条曲线可以在通道间复制；全局只能「保存到 config.json」或「全部交由 BIOS 控制」。

因此缺的是：**没有一次改所有风扇的入口**，也没有「把整套调校命名保存并来回切换」的能力。

同时存在三个真实的理解风险（也就是你提出的注意点）：

1. 若再引入全局「安静 / 标准 / 性能」，用户会自然地把它们和单扇预设当成一一对应。
2. 若单扇预设看起来像「标准模式」，用户改完曲线后会以为自己改坏了预设。
3. 「预设」「配置」「保存」如果都叫得很像，用户分不清哪份是只读的、哪份是自己的。

## 3. 设计取舍：让「一一对应」变成真的

### 3.1 统一预设与单扇预设：不是回避对应，而是同源

你的第一反应是「用户会不会误认为一一对应」，并说「不过倒是也可以，标准预设的值不可以修改」。这个判断是对的，我们**直接让它一一对应，并且是事实上的一一对应**：

- Core 里只有一套 `CurveTemplates`（静音 / 均衡 / 性能），**全局场景和单扇模板引用同一份曲线值**（single source of truth）。
- 「内置场景 · 静音」的定义就是：所有未锁定通道 → 模式切为温度曲线 + 套用「静音」模板。
- 名字也严格一致，不用「标准」而用「均衡」：一是和已有单扇预设对齐，二是「标准」容易被理解成「默认/不可动」，而「均衡」天然表达取舍。你提到的安静 / 标准 / 性能，对应为 **静音 / 均衡 / 性能**。

这样即使用户认为「全局静音 = 每个风扇用单扇静音」，也不会产生错误行为，因为这就是真的。反过来，如果故意做两套不同的值，才会制造「同样是静音，为什么全局和单个不一样」的认知陷阱，所以**刻意不做两套值**。

内置场景的值**不可修改**：没有「保存到内置场景」的入口，也没有编辑按钮。想改就另存为「我的配置」。

### 3.2 单扇预设只导入值，不修改模板本身

- 曲线编辑器中的三个模板按钮**只做一件事：把值填进当前编辑的曲线**。它们不是单选按钮，不保留选中态，不写回模板。
- 没有「保存模板」入口，模板是代码内置的只读对象，程序升级可以统一改进它们。
- 编辑器实时显示来源：`当前曲线：与「静音」模板一致` / `当前曲线：自定义（未套用模板）`。
- 用户点模板 → 再拖两个点 → 点确定，结果只是**这个通道的当前方案**变了；内置模板纹丝不动。
- 去掉原来重复的「恢复默认」按钮（它和「均衡」等价），避免「到底是恢复默认还是套均衡」的第二重歧义。

### 3.3 用户如何感知「预设」和「自定义配置」的区别

靠四层信息叠加，而不是只靠一句说明：

1. **词汇三分，不混用**：只读的叫「内置场景」或「模板」；用户的可写对象只叫「我的配置」；正在编辑的只叫「当前方案」。UI 主标签中不再出现笼统的「预设」二字。
2. **视觉类型标识**：统一下拉列表里，内置场景带「内置 · 只读」徽标，我的配置带「我的」徽标和更新时间；只读对象没有可用的「重命名/删除」入口（按钮禁用）。
3. **行为规则是硬约束，不靠自觉**：
   - 「另存为…」永远生成**新的我的配置**，绝不会覆盖内置场景；「保存」只把当前修改写回当前选中的「我的配置」；
   - 内置场景不可编辑、不可删除；
   - 配置命名禁止与内置场景重名（静音 / 均衡 / 性能 / BIOS 默认），提示语明确说「这是内置场景名，为避免混淆请换一个名字」。这一条直接消除「我是不是把内置的静音改掉了」的担心。
4. **「场景 / 配置」下拉框就是状态本身**：当前选中项即当前来源，内置场景项带「内置 · 只读」类型徽标，我的配置项带「我的」徽标和更新时间。选中即切换，不再需要单独的「应用」按钮；只有当前「我的配置」有未保存修改时，才在旁显示一个小号琥珀色「已修改」徽标。
5. **每个风扇也有来源提示**：曲线列第二行显示 `模板 · 静音`（青色）或 `自定义曲线`（琥珀色），用户能看出是整条模板还是被单独改过。

另外，**切换**是有代价的操作：当前方案有未保存修改时，切换会弹确认框，明确说「会覆盖当前方案，但已保存的『我的配置』不受影响」。这既是防误触，也是在反复强化两者的区别。

### 3.4 选中内置场景后想改怎么办：拦截 + 复制

内置场景是只读「文档」，不是可编辑草稿。用户在内置场景生效时尝试修改通道（模式 / 温度源 / 固定 PWM / 曲线 / 复制曲线）会被**直接拦截**：

> 内置场景「静音」是只读的，不能直接修改。是否复制为「我的配置」后继续编辑？

选「是」会以当前场景值为内容创建一个新的「我的配置」（默认名「静音 · 我的」），切换过去后即可正常编辑；选「否」则本次操作不生效。这样用户永远不会处于「改着改着把预设改了」的状态，也不会出现「已修改的内置场景」这种不存在的概念。「锁定」是通道安全属性，不拦截，随时可设置。

## 4. 数据模型

`%LocalAppData%\Atlas\config.json` 增量字段（旧配置文件无这些字段时自动兼容）：

```jsonc
{
  "PollMs": 1000,
  "Fans": [ /* 每个通道：Mode / FixedPercent / SourceId / MinPercent / MaxPercent / Curve / Protected / CustomName */ ],

  // 当前方案来源（二选一，可都为空 = 未归档的自定义方案）
  "ActiveSceneId": "builtin.balanced",
  "ActiveProfileId": null,

  // 应用/保存那一刻所有通道热设置的指纹（SHA-256）。相等=未修改，不等=已修改
  "StateFingerprint": "9f2c…",

  "Profiles": [
    {
      "Id": "profile-8f3a…",
      "Name": "夜间安静",
      "CreatedAt": "2026-11-09T21:10:00+08:00",
      "UpdatedAt": "2026-11-09T22:42:00+08:00",
      "Fans": [
        {
          "FanId": "/lpc/nct6798d/control/0",
          "FanName": "Fan #1 (前风扇)",
          "Settings": {
            "Mode": 2,
            "FixedPercent": 50,
            "SourceId": "…/temperature/0",
            "MinPercent": 20,
            "MaxPercent": 100,
            "Curve": [ { "Temp": 30, "Percent": 20 }, … ]
          }
        }
      ]
    }
  ]
}
```

关键语义：

- **快照只包含「热设置」**：模式、固定 PWM 值、温度源、曲线上下限、曲线点。**不包含** `Protected`（锁定）和 `CustomName`——前者是安全属性，后者是 v0.2 的备注名（UI 已移除编辑入口，仅保留字段兼容旧配置），都不该被场景切换悄悄改掉。
- **锁定通道不参与应用**：应用场景/配置时跳过 `Protected` 通道，状态栏报告「跳过 N 个锁定通道」。水泵之类先锁定，就不会被一键场景带走。
- **缺失/新增通道**：配置按 `FanId` 匹配。配置里有、当前机器没有的通道计为「不可用」；当前有、配置里没有的通道保持原样（不重置），状态栏报告数量。部分覆盖时「当前来源」仍标注为该配置（未包含的新通道保持原样）——来源表达的是「最近一次应用的对象」，不是逐通道的精确归属，这是有意的简化。
- **没有任何通道真正应用时**（全部锁定 / 没有通道 / 配置条目全部失效），不会把「当前来源」标记成该场景或配置，避免状态栏假装成功。
- **场景保留安全上下限**：应用场景只切换模式与曲线，保留每个通道的 `MinPercent` / `MaxPercent`（当前 UI 不暴露，默认 20–100）。如果手工改过下限，场景的静音值会被下限夹取——这是有意保留的安全边界，即「场景 = 模板值 ∩ 通道上下限」；文档明确这一点，不承诺绝对转速。
- **失效温度源自愈**：场景/配置带回本机不存在的温度源 Id 时，应用后自动回退到默认 CPU 温度源，避免引擎在 5 秒后全速兜底。
- **指纹只算热设置**：改备注名、勾选锁定不会让状态变成「已修改」；改模式/曲线/温度源才会。
- **未归档的草稿也有基线**：首次加载/旧配置升级时，把当时的设置记为基线。之后用户手工调整（哪怕还没保存成配置）也会被判定为「已修改」，套用场景/配置时先确认，不会静默覆盖。
- **应用即保存**：切换场景/配置、保存配置/另存为后立即写 `config.json`，与现有自动保存习惯一致。

## 5. 交互设计

### 5.1 场景与配置栏（主窗口，提示条与风扇表格之间）

```
┌──────────────────────────────────────────────────────────────────────────────────────┐
│ 切换配置  [● 内置·只读 静音 ▾]  [已修改]   [保存]  [另存为] [重命名] [删除]        │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

- **只保留一个下拉框**：标签为「切换配置」，内置场景项带「内置 · 只读」类型徽标，我的配置项带「我的」徽标和更新时间；当前没有来源时显示「未归档」占位项。**选中即切换**，没有单独的「应用」按钮，也没有重复的「当前方案」状态文字。
- 只有当前「我的配置」有未保存修改时，才在下拉框旁显示一个小号琥珀色「已修改」徽标（tooltip 提示可点「保存」写回）；内置场景不可编辑，永远不会出现「已修改的内置场景」。
- 「另存为」：把当前设置另存为一个新的「我的配置」；对内置场景来说就是「复制成可编辑配置」。
- 「保存 / 重命名 / 删除」：只对选中的「我的配置」可用；内置场景项与未归档占位项禁用。「保存」把当前修改写回该配置（不新建）。
- 表格标题栏移除原来的「保存配置 / 保存修改」按钮：保存动作统一由「另存为」/「保存」承担，避免两个「保存」语义打架。
- 表格标题栏按语义分组：左侧是查看类（风扇通道、通道数、隐藏 0 RPM），右侧是操作类（复制曲线、全部交由 BIOS 控制）。
- 开机启动这类全局应用设置不再占用表格工具栏：入口放在窗口标题栏的「设置」，打开设置窗口后勾选「开机启动 Atlas」（计划任务 AtlasFan，登录时以管理员权限启动，不弹 UAC）。
- 模式与列联动：固定 PWM 列只在「固定 PWM」模式下可操作、曲线列只在「温度曲线」模式下可操作，另一列置灰/禁用，让用户一眼看出当前真正生效的是哪一列。
- 温度源收敛：显卡通道固定使用该显卡的 GPU Core（下拉禁用，避免误选 CPU 温度）；主板通道只提供 CPU Package / GPU Core 两个实用选项，隐藏 P/E 核、Hotspot、显存等细节传感器。
- 升级兼容：温度源收敛（显卡改 GPU Core、细节源回落 CPU Package、AMD 平台自动识别 Tctl/Tdie）发生在建立状态基线之前，归一化本身不算用户修改，不会让状态显示「已修改」。温度源只影响配置与展示，锁定通道的源归一也不会写 PWM。
- 切换有未保存修改的「我的配置」或未归档草稿时，先确认是否丢弃；取消则下拉选择回退到当前项。

### 5.3 四条典型动线

1. **新机器，一键安静**：打开 Atlas → 下拉选「内置场景 · 静音」→ 选中即切换，所有未锁定通道变成温度曲线 + 静音曲线 → 状态栏显示已应用 N 个。
2. **只想让尾风扇安静**：点某行「编辑…」→ 点模板「静音」→ 拖低 60°C 点 → 确定。该风扇曲线列变「自定义曲线」，其他通道不变；内置模板不变。
3. **保存自己的方案**：调好所有风扇 → 「另存为…」→ 输入「夜间安静」→ 下拉里多出该项并自动选中。以后从下拉选它即可一键回到该配置。
4. **在配置上继续改**：当前为「夜间安静」→ 把 Fan #2 改成固定 40% → 出现「已修改」徽标 → 点「保存」写回该配置，或点「另存为…」另建一个新配置（原配置保留）。
5. **从预设开始改**：下拉选「内置场景 · 静音」→ 直接改模式/曲线 → 被拦截 → 提示是否复制为「我的配置」→ 复制后继续编辑；原内置场景始终不变。

## 6. 边界、安全与失败处理

- **锁定通道优先**：场景/配置都不写锁定通道；这保持 v0.2 的「锁定=永不写」安全契约。首次使用场景前建议先确认疑似水泵的通道（如本机 Fan #7）接线，并勾选锁定。
- **场景不是 BIOS 默认**：场景仍是 Atlas 软件控制；「全部交由 BIOS 控制」保持独立按钮（把手交还 BIOS、界面显示未接管）。两者语义不同，不混在一起。
- **切换前确认**：当前「我的配置」有未保存修改、或未归档草稿被手工改过时，切换场景/配置前确认，避免丢改动；内置场景本身只读，不存在「切换丢失预设修改」。
- **没有可接管通道时**：全部通道被锁定、或配置里没有任何可用通道时，选择场景/配置会回退下拉并明确提示「未应用」，不会出现「已应用 0 个通道」这种假成功。
- **预设编辑拦截**：内置场景生效时，模式/温度源/固定 PWM/曲线编辑/复制曲线/「全部交由 BIOS 控制」都会被拦截并引导先复制为「我的配置」；「锁定」不拦截（安全属性，允许随时设置）。锁定通道的热设置同样不修改，保证内置场景期间不会出现「预设 + 已修改」。
- **落盘时机（有意取舍）**：按用户反馈移除了独立的「保存修改」按钮；配置在切换场景/配置、保存配置/另存为、全部交由 BIOS 控制、退出应用时写盘。极端崩溃可能丢失最后一段尚未归档的修改，这是简化 UI 的代价，后续可用「变更后防抖自动保存」补齐。
- **全部交由 BIOS 控制后**：所有通道模式改回 BIOS 默认并交还控制权。若当前来源是「我的配置」，**保留该来源并显示「已修改」**，点「保存」即写回该配置（不会新建配置，也不会未经确认覆盖快照）；若当前来源是未归档草稿，则保持未归档并把当时的热设置记为基线。当前来源是内置场景时，按「预设编辑拦截」处理——先引导复制为「我的配置」，本次操作不生效。
- **删除当前配置后**：当前设置保持不动，来源清空、基线同步为当前值（干净未归档）。
- **命名规则**：1–24 字符；禁止与内置场景同名；禁止与已有配置同名（大小写不敏感）；拒绝控制字符与零宽等不可见字符；连续空白会折叠（避免「BIOS  默认」绕过保留名）；自动 trim。
- **旧配置 / 手工 JSON**：无 `Profiles` 字段时按空处理；`Enabled` 旧字段迁移逻辑保留；null 集合项、null 曲线点、重复 Id、悬空活动来源由 `Normalize()` 修复，不会因一条坏数据丢掉整份配置。

## 7. 考虑过但放弃的方案

| 方案 | 问题 | 结论 |
| --- | --- | --- |
| 只做全局配置，不内置场景 | 新用户必须自己从零建「静音」，失去一键价值 | 放弃 |
| 内置场景允许直接编辑 | 用户不知道改的是模板还是当前状态；升级/重置语义崩坏 | 放弃 |
| 单扇预设与全局场景各用一套值 | 制造「同名不同值」的认知陷阱 | 放弃 |
| 全局配置自动按程序/温度切换、无「当前方案」 | 缺草稿态，用户改一点就生效且无处保存，容易误改 | 暂缓，作为后续扩展 |
| 把场景做成 Tab（切换即切换全部） | 与「编辑中」状态冲突，容易丢失临时修改 | 放弃 |
| 场景按钮 + 独立「应用」按钮 + 「当前方案」状态文字（v1） | 下拉选中项已经表达当前来源，多一步操作与重复信息 | 放弃（v2 改为选择即切换、去掉状态文字与保存按钮） |

## 11. 一句话回答你的三个疑虑

1. **会不会误认为统一预设和单扇预设一一对应？** 会，而且我们让它真的对应：两处引用同一套只读曲线值，名字一致，场景 = 所有未锁定通道套用同名模板 + 温度曲线模式。用户怎么理解都不会遇到「同名不同值」。
2. **单扇预设会不会被改掉？** 不会。模板只读；内置场景生效时任何通道编辑都会被拦截并引导先复制为「我的配置」，不存在写回模板/预设的入口。
3. **怎么让用户感知预设 vs 自定义配置？** 统一下拉里的类型徽标（内置 · 只读 / 我的 / 未归档）、内置不可覆盖且禁止同名配置、「已修改」只出现在我的配置上、每行显示曲线来源。核心规则一句话：**只读的永远是预设，能编辑的只有「我的配置」，想改预设就先复制。**

## 12. 独立评审后的修正（已合入本分支）

在 UI 完成前让独立 verifier 对 Core 语义、设计文档和离屏渲染做了对抗性评审，以下问题已修正：

| 评审发现 | 修正 |
| --- | --- |
| 未归档草稿永远不判「已修改」，套用场景会静默覆盖 | `AtlasConfig.EnsureStateBaseline()` 在硬件枚举/默认温度源补齐之后建立基线；未归档方案的手工修改也判「已修改」并弹确认；删除当前配置后基线同步为当前值 |
| `ApplyScene` 保留 `MinPercent` 会把「静音」夹到 40% | 保留上下限是有意为之的安全边界，已在数据模型与文案中明确「场景 = 模板值 ∩ 通道上下限」；同时补上失效温度源自动修复 |
| 全部锁定 / 无通道时仍声称「当前 = 该配置」 | `ApplyScene`/`ApplyProfile` 仅在实际应用 ≥1 个通道时才更新来源 |
| Normalize 对 null 防护不对称，一条坏数据会丢掉整份配置 | 清理 null 风扇、null 曲线点、重复 Id、重复 FanId，并统一互斥的悬空来源 |
| 零宽字符可绕过保留名/重名校验 | 拒绝 Format/Control 字符；空白折叠后再比对保留名与重名 |
| `CurveTemplates.Match` 遇到 NaN 反而判「一致」 | 匹配前要求所有点有限 |
| MinWidth=1180 时状态文字被裁切、下拉框时间被截断 | 状态 hint 移入 tooltip，下拉框只显示配置名（更新时间放 tooltip），场景/配置区宽度收紧 |
| 基线在硬件枚举前建立，全新安装/新增通道首启误报「已修改」 | 基线改到 `BuildRows()` 之后建立；已有会话基线不被覆盖，跨重启的真实修改仍保留 |
| 温度源自动修复改 SourceId 后基线过期，套用后立刻显示「已修改」 | 应用并修复温度源后刷新基线；修复逻辑跳过锁定通道 |
| 「保存」配置在换硬件后会静默丢弃缺失通道设置 | 保存确认框提示「N 个通道当前不可用，保存后会从配置移除」 |
| `Match`/`Fingerprint` 对未 Normalize 的 null 项仍可能 NRE | 两处都过滤 null 风扇/曲线点（Load 路径本已 Normalize，双保险） |

## 14. 撤销 / 重做（2026-11-12 追加）

**结论**：撤销 / 重做只服务「当前方案」，不跨越来源切换，也不跨越保存。

- **数据**：每一步是当前方案所有通道的完整热设置快照（模式 / 固定 PWM / 温度源 / 上下限 / 曲线）。刻意**不包含备注名与锁定**——它们是通道身份 / 安全属性，撤销一次模式修改不应该把水泵解锁。
- **结构**：`FanEditHistory` = 线性快照列表 + 游标。撤销 / 重做只移动游标；新操作截断游标之后的重做分支；最多 1024 步，超出丢最旧。
- **粒度 = 用户的每个操作**：模式 / 温度源下拉选择立即提交一步；固定 PWM 滑杆拖动在鼠标释放或安静 250ms 后合并成一步；曲线编辑器「确定」、复制曲线到多个通道、「全部交由 BIOS 控制」都各算一步。
- **重置**：启动、应用内置场景 / 我的配置、复制为「我的配置」、另存为、保存 → 当前设置成为唯一基线，撤销 / 重做不可用。其中「保存后清空」是有意取舍——历史只在两次保存之间有效。
- **只读场景**：内置场景生效期间编辑被拦截，历史保持空基线，撤销 / 重做按钮禁用。
- **与「已修改」的关系**：撤销 / 重做后仍由 `StateFingerprint` 比较决定是否显示「已修改」，不额外维护状态。
- **入口**：工具栏「撤销 / 重做」按钮 + Ctrl+Z / Ctrl+Y（`ApplicationCommands.Undo/Redo` 命令绑定）；文本框聚焦时 Ctrl+Z 仍由文本框自身处理。
- **边界**：撤销只改配置，引擎下个 tick（≤1s、8%/s 斜坡）才生效；历史不持久化，重启清空；撤销 / 重做不单独写盘，退出时随配置落盘。
